# 产品目标与设计上下文

以下记录产品目标、架构边界与实施顺序；分层消息配置与 message CLI 已实现，发布流程仍待实现。已实现的开发流程见 `specs/development-workflow/spec.md`。

## 需求与验收条件

### 目标

维护者需要给多个维护分支发布补丁：确认改动已经合入远端、找到各分支上一正式 tag、计算下一版本、推送 tag，并把本次变更整理成统一格式的消息。

现在这些步骤依赖人工和工作流说明，容易选错版本线、漏掉提交、重复发布或在重试时生成不同内容。rls 将选择与执行分离，并保存可追溯结果。

### 使用场景

1. 同一修复合入多个维护分支后，一次计划并发布多个 tag。
2. 某些分支尚未合入；只发布满足条件的分支，并明确报告其余分支的原因。
3. 发布完成后调整消息模板，重新生成同一批发布的通知。
4. 部分 tag 推送失败，修复连接后继续执行原计划。
5. 后续为 Cargo 或其他构建体系统一管理发布结果与通知。

### 首期范围

- 本地 Git 仓库，指定 remote，显式选择目标分支。
- 配置分支与版本线的映射，例如 `5.6 → v5.6.0.*`、`5.6-2sync → v5.6.1.*`。
- 从远端目标提交的祖先中选择符合该版本线的上一正式 tag；按数字版本比较，不混入日期 tag 或其他分支的 tag。
- 默认递增补丁号；首次发布、历史不单调或存在歧义时要求显式指定基线与版本，不能猜测。
- changelog 默认包含 `previous_tag..target_sha` 的全部提交，按历史顺序输出 subject，并保留 SHA 供追溯；不默认为单条提交，也不要求 Conventional Commits。
- 生成并保存计划，展示每个分支的目标 SHA、前后 tag、提交列表及 tag/push 动作。
- 执行计划中的轻量 tag 创建和推送，逐项记录结果，支持重试。
- 从发布记录渲染模板，输出终端或文件，按需复制到剪贴板。
- 允许从明确指定的新旧 tag 导入历史发布记录，支持现有发布补发消息。

### 执行约束

- 以指定远端分支为发布依据，不将本地领先提交自动当成已合入，也不执行评审或合入。
- 仅判断远端存在提交不足以判断某项修复已合入。计划支持指定必须包含的提交；未指定时只承诺发布远端版本，不声称包含某个工单。
- 不切换用户分支，不 stash，不修改无关工作区。`git-tag` 可从已有对象操作；需要修改文件的后端使用隔离检出。
- `plan` 可以获取远端引用，但不能修改源码、创建 tag 或发布制品。
- `run` 开始前核对远端目标 SHA、基线 tag 和配置指纹；计划过期时停止该项，要求重新规划。
- 同名 tag 指向同一提交时视为该步骤已完成；指向不同提交时失败，绝不自动覆盖或强推。
- 目标提交等于上一 tag 时报告无新变更；不得创建空发布。
- 发布动作不视为跨分支事务。部分成功时保留已发布结果，不自动删除远端 tag。
- 默认消息仅包含成功发布的项目；失败和跳过项单独报告。若模板渲染或剪贴板失败，可以独立重试，不重做发布。
- 提及的人、项目名称和消息措辞均由配置或模板提供，工具不内置个人信息，也不自动发聊天消息。

### 首期验收

- 两条版本线能正确生成各自下一 tag，且排除另一条线及日期格式 tag。
- 多个提交均出现在对应发布的 changelog 中，模板保持配置的排序和空行。
- 使用本地 bare remote 验证真正的 tag 推送和远端 SHA，无需内网服务。
- 未合入的指定提交、过期计划、冲突 tag、无变更、部分失败均有明确且可测试的结果。
- 同一计划重复执行不会重复发布；同一发布记录重新渲染不会重新访问发布后端。
- 整个 tag 流程保持用户原分支与未提交文件不变。

### 后续与非目标

第二阶段验证 `cargo release` 集成；其他语言后端按真实项目需求增加。首期不实现制品仓库、Jenkins 调度、聊天机器人、动态插件市场或替代 cargo-release 的 Rust 发布算法。

## 架构与扩展边界

### 决策

rls 是独立工具，不扩展 crsu 的评审职责。二者可以读取同一 Git 仓库，但无需相互调用。

首期用 Rust 构建单一 CLI crate；按职责划分模块，不提前拆成多个 crate。版本与标签操作使用结构化参数调用 Git，不将配置插值为 shell 命令。

### 核心数据

| 类型 | 内容 |
| --- | --- |
| ReleasePlan | schema 版本、计划 ID、仓库标识、配置指纹、有序发布项和生成时间 |
| ReleaseItem | 后端、远端、目标分支和 SHA、要求包含的提交、上一 tag 及 SHA、下一版本和 tag、提交列表、动作 |
| ReleaseRecord | 计划引用、每项实际版本和 SHA、每步状态、已验证的远端结果、失败原因 |
| MessageContext | 项目与模板变量、成功发布项、版本、tag、完整提交列表 |

计划保存在仓库本地 `.rls/state/`，不提交 Git。计划固定内容，执行进度另存；数据包含 schema 版本并采用原子写入。记录不保存凭据，认证复用 Git 或后端已有机制。

### 模块职责

- `config`：发现共享 Git 元目录与全局配置，合并消息字段并保留路径来源，校验分支版本规则与模板路径。
- `planner`：形成发布计划，统一校验前置条件和必需输入。
- `git`：读取远端引用、祖先关系、tag 与提交，不承担 UI 或模板逻辑。
- `runner`：执行有序动作，持久化进度，核对结果并支持恢复。
- `backends`：提供项目相关的规划与执行能力，首期只有 `git-tag`。
- `message`：从发布记录构造稳定数据，渲染模板和输出。
- `store`：管理计划及发布记录的序列化与迁移。

### 后端契约

接口应支持三个操作：生成项目相关计划、执行动作、探测动作是否已完成。具体 Rust trait 在第二种后端接入时定型，首期不引入动态加载协议。

每个动作明确其执行方。`git-tag` 由 rls 创建和推送 tag；Cargo 模式中若由 cargo-release 创建 tag，rls 不再重复创建。所有后端都必须返回实际版本、提交、tag 和发布结果，而不是仅返回一段终端输出。

Cargo 后端不能简单复用“直接给远端 HEAD 打 tag”的模型：它可能修改版本文件、创建发布提交，并为 workspace 发布多个包。计划要记录起始提交与预计修改，执行后再记录最终提交；消息中的 changelog 应使用已验证的最终区间。

第一阶段的单分支版本规则并不代表未来只能发布单个包。第二阶段通过真实 workspace 验证发布项与包的映射，再扩展 schema。

### 仓库级与全局消息配置（已实现）

沿用 crsu 的目录约定：通过 Git 发现共享元数据目录，在 `<git-common-dir>/rls/config.toml` 读取仓库配置。普通仓库对应 `.git/rls/config.toml`；linked worktree 共用主仓库配置，不假设工作区中的 `.git` 是目录，也不依赖当前工作目录。根目录 `rls.toml` 不参与默认发现。

全局配置位于用户配置目录下的 `rls/config.toml`：Linux 使用 `${XDG_CONFIG_HOME:-~/.config}/rls`，macOS 使用 `~/Library/Application Support/rls`，Windows 使用 `%APPDATA%\rls`。非空 `RLS_CONFIG_HOME` 可直接指定 rls 全局目录，配置文件为 `$RLS_CONFIG_HOME/config.toml`。不读取 crsu 的配置或凭据。

消息配置使用 `[message].version = 1` 独立标记格式，省略时按 v1 解释；全局与仓库层分别校验，未知版本报错，不参与字段继承。顶层 schema_version 仍管理整个配置文件结构。

消息由 `[message].template` 和 `[message.variables]` 配置。模板字段按仓库、全局、内置模板的顺序选择；变量按键合并，仓库同名键覆盖全局，显式空字符串保留，字段缺失才继承。内置模板提供版本与完整 changelog，不内置称呼、个人信息或项目专用文案。与 crsu 当前的整文件选择不同，消息配置采用字段合并，允许仓库只改称呼而继承全局模板。

相对模板路径始终相对于**声明该模板的配置文件所在目录**解析；继承的全局模板仍相对于全局目录，不会因仓库覆盖变量而改变基准。支持绝对路径。模板中的称呼、项目文案、布局和空行均可定制；运行数据 `releases` 由发布记录提供，配置变量只进入 `variables`，不能覆盖发布结果。

配置文件不存在时继续使用下一层；已有配置解析失败、不支持的 schema、显式模板不存在或渲染时缺少变量均报错并指出来源，不静默回退。仓库外可以读取全局消息设置，但生成发布消息仍需要明确的发布记录。项目身份、分支版本线等发布配置保留在仓库层，全局示例仅提供消息默认值。

`message` 每次按当前有效配置重新渲染已保存的发布记录，不访问发布后端、不重复打 tag。未来 planner 的配置指纹应只包含影响发布动作的设置，消息模板或变量变化不会令发布计划过期。发布状态存储路径仍按本节之外的既有设计，消息配置位置不隐式迁移状态。

验收场景（除未来 planner 指纹外已由 Cucumber 覆盖）：

- 只有全局模板时，仓库继承该模板和变量。
- 仓库只覆盖 `greeting` 时，全局模板及其他变量仍生效；空字符串可清空称呼。
- 仓库指定模板时使用仓库模板；全局模板被继承时使用全局路径基准。
- 从仓库子目录或 linked worktree 运行时，均读取相同的共享元目录配置。
- 两层均未指定模板时使用内置模板；显式模板缺失或 TOML 损坏时失败。
- 修改消息配置后，同一发布记录可重新渲染，发布后端调用次数不增加。
- 修改消息配置不使计划过期，修改发布相关设置仍触发过期检查。

### 模板

配置采用 TOML。消息模板采用 MiniJinja 的 Jinja 风格语法：支持遍历发布项、访问变量与格式化文本，不执行 shell、不读取任意环境变量。使用严格未定义变量检查，保留模板尾部换行。

消息生成是纯粹的记录到文本转换。输出文件与剪贴板是独立动作，失败不改变发布状态。

### 与 cargo-release 的边界

先验证其实际 CLI、dry-run 行为、workspace 支持及结果获取方式，再实现适配器；当前不承诺任何尚未核对的命令参数。

优先调用工具提供的能力，不复制其版本更新、依赖联动与包发布逻辑。非 Rust 后端遵循相同边界；不以任意 shell hook 代替发布状态模型。
