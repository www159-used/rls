# 需求与验收条件

## 目标

维护者需要给多个维护分支发布补丁：确认改动已经合入远端、找到各分支上一正式 tag、计算下一版本、推送 tag，并把本次变更整理成统一格式的消息。

现在这些步骤依赖人工和工作流说明，容易选错版本线、漏掉提交、重复发布或在重试时生成不同内容。rls 将选择与执行分离，并保存可追溯结果。

## 使用场景

1. 同一修复合入多个维护分支后，一次计划并发布多个 tag。
2. 某些分支尚未合入；只发布满足条件的分支，并明确报告其余分支的原因。
3. 发布完成后调整消息模板，重新生成同一批发布的通知。
4. 部分 tag 推送失败，修复连接后继续执行原计划。
5. 后续为 Cargo 或其他构建体系统一管理发布结果与通知。

## 首期范围

- 本地 Git 仓库，指定 remote，显式选择目标分支。
- 配置分支与版本线的映射，例如 `5.6 → v5.6.0.*`、`5.6-2sync → v5.6.1.*`。
- 从远端目标提交的祖先中选择符合该版本线的上一正式 tag；按数字版本比较，不混入日期 tag 或其他分支的 tag。
- 默认递增补丁号；首次发布、历史不单调或存在歧义时要求显式指定基线与版本，不能猜测。
- changelog 默认包含 `previous_tag..target_sha` 的全部提交，按历史顺序输出 subject，并保留 SHA 供追溯；不默认为单条提交，也不要求 Conventional Commits。
- 生成并保存计划，展示每个分支的目标 SHA、前后 tag、提交列表及 tag/push 动作。
- 执行计划中的轻量 tag 创建和推送，逐项记录结果，支持重试。
- 从发布记录渲染模板，输出终端或文件，按需复制到剪贴板。
- 允许从明确指定的新旧 tag 导入历史发布记录，支持现有发布补发消息。

## 执行约束

- 以指定远端分支为发布依据，不将本地领先提交自动当成已合入，也不执行评审或合入。
- 仅判断远端存在提交不足以判断某项修复已合入。计划支持指定必须包含的提交；未指定时只承诺发布远端版本，不声称包含某个工单。
- 不切换用户分支，不 stash，不修改无关工作区。`git-tag` 可从已有对象操作；需要修改文件的后端使用隔离检出。
- `plan` 可以获取远端引用，但不能修改源码、创建 tag 或发布制品。
- `run` 开始前核对远端目标 SHA、基线 tag 和配置指纹；计划过期时停止该项，要求重新规划。
- 同名 tag 指向同一提交时视为该步骤已完成；指向不同提交时失败，绝不自动覆盖或强推。
- 目标提交等于上一 tag 时报告无新变更；不得创建空发布。
- 发布动作不视为跨分支事务。部分成功时保留已发布结果，不自动删除远端 tag。
- 默认消息仅包含成功发布的项目；失败和跳过项单独报告。若模板渲染或剪贴板失败，可以独立重试，不重做发布。
- 提及的人、项目名称和消息措辞均由配置或模板提供，工具不内置个人信息，也不自动发聊天消息。

## 首期验收

- 两条版本线能正确生成各自下一 tag，且排除另一条线及日期格式 tag。
- 多个提交均出现在对应发布的 changelog 中，模板保持配置的排序和空行。
- 使用本地 bare remote 验证真正的 tag 推送和远端 SHA，无需内网服务。
- 未合入的指定提交、过期计划、冲突 tag、无变更、部分失败均有明确且可测试的结果。
- 同一计划重复执行不会重复发布；同一发布记录重新渲染不会重新访问发布后端。
- 整个 tag 流程保持用户原分支与未提交文件不变。

## 后续与非目标

第二阶段验证 `cargo release` 集成；其他语言后端按真实项目需求增加。首期不实现制品仓库、Jenkins 调度、聊天机器人、动态插件市场或替代 cargo-release 的 Rust 发布算法。
